# Terra Astra: general answering and tracking evaluation

Created 2026-09-13. Specification only; these scenarios have NOT been run as an evaluation suite. Examples are test inputs, never product routing rules. No fixed response text, coordinates, counts or named data provider is an expected answer. Existing decorative aircraft and orbital particles do not satisfy real tracking.

## Evaluation contract

Run each initial query and its follow-ups in one conversation, both typed and spoken. Evaluate the answer, the rendered globe and the audio together. Then start a fresh conversation for the next case. Resolve relative dates against the run's recorded time and timezone. Preserve follow-up context explicitly: entity, occurrence, location, time, units, selected layers and tracking mode.

Stateful cases require an explicit fixture before the quoted query. F03 starts with one displayed flight occurrence selected from a timestamped live-candidate result, including its stable occurrence ID, callsign and ICAO24 when available. F04 starts with a currently tracked moving object and active follow subscription. S03 starts in the same conversation as a successfully resolved satellite follow; its catalogue identity and orbital-element epoch are retained. X01 starts with a selected, successfully updating aircraft or satellite and then injects the specified feed fault. X03 starts with a recorded viewport, visible place/entity selection and an in-progress answer. If a fixture cannot be established, mark the prerequisite unavailable and do not award the dependent capability; never invent the missing referent.

For each run retain: build identifier; question and transcript; request/turn ID; chosen route/model; actual native subagent completion events when applicable; resolved entity IDs; retrieved source URLs and retrieval times; observation times or orbital-element epochs; normalized records and units; issued WorldCommands and completion/rejection times; answer/audio timing; screenshots or video; cancellation/cleanup result. Redact credentials and personal account data. A model's claim that it used a source, delegated, or moved the camera is not evidence of those actions.

The answer model chooses tools and a visual plan. Data adapters resolve entities and normalize observations. A validated WorldCommand interpreter renders reusable primitives. Application code must not import this eval file or branch on its questions, names or expected outcomes.

## Anti-hardcoding and holdout protocol

1. Freeze the build before choosing holdout entities. Evaluation fixtures are isolated from app code and prompts. Do not feed expected outcomes to the answer model.
2. Keep these 20 cases as development examples. For scored runs, create at least 10 unseen variants after the freeze: different region/hemisphere/script, airline/date, satellite class/catalogue identifier, time range and comparison metric. Record the random seed and chosen inputs in the evaluation report, not production configuration.
3. Resolve fresh flight candidates from a configured service and satellite candidates from a current catalogue. Keep the named-flight case even when grounded/missing: it tests identity and availability; F02 supplies an active-flight test when the service has coverage.
4. Paraphrase each query; test spoken aliases and airline number versus callsign; change one entity/date while preserving syntax. Camera and data must change accordingly. Unsupported aliases should lead to clarification, not a confident wrong entity.
5. Run metamorphic checks: reorder comparisons, request metres then feet, substitute tomorrow for today, replay the same satellite at the same UTC instant, change observer city, and revisit a corrected ambiguous place. Assert appropriate changes and invariants without a stored answer string.
6. Test provider failure, empty results, stale records, conflicting sources, rate limits and latency. An accurate unavailability response can pass integrity, but it does NOT pass the missing visualization/tracking capability. Report separate capability coverage.
7. A source adapter, coordinate math, schema, rendering primitive and provider-specific authentication may be fixed code. The selected answer, place, route, track, metric value and generated image must derive from runtime context/evidence.

## Scoring and release gates

Score each dimension 0 (wrong/missing), 1 (partial) or 2 (meets case): answer/evidence; entity/time resolution; visual explanation; follow-up/voice continuity; interaction/control. Maximum 10 per case. Keep a separate complete/partial/unavailable/error capability status, and log which source prerequisites were actually available. A missing feed cannot receive a complete tracking score even if the error message is excellent.

Critical failure in any case overrides its numerical score: wrong moving-object identity; invented live position/count/route; generated image presented as source evidence; stale turn replacing a newer turn; camera continuing after Stop; falsely claimed source/delegation/camera success. These block release of the affected advertised capability.

Suggested product targets, not measured results: visible input acknowledgement within 300 ms; first useful text/audio within 5 seconds for quick answers; first useful researched explanation within 15 seconds when sources respond; final research within 90 seconds; local stop/interrupt within 500 ms; 30+ fps on the agreed demo device. Track p50/p95 separately by route and input mode over repeated runs. Measure time to first useful content, not filler. Log camera-settled and image-ready separately so slow asset generation does not block text/audio.

Tracking updates must follow the provider's allowed cadence and available observation freshness, not a blanket promise of second-by-second data. Set freshness and positional tolerances BEFORE testing based on provider/record type. A flight test needs multiple fresh observations; a satellite propagation test needs agreement with independent math at several timestamps. No per-frame LLM calls: follow motion is a deterministic renderer/data loop after model-driven entity selection.

For every narration beat, capture its related visual command and readiness acknowledgement. Spatial narration must refer to the current visible entity/view, not an image still loading or an old scene. Keep text, audio, generated images and camera on the same turn revision.

Recommended first evaluation sweep: G01, G03, G07, G08, F01, F02, F04, S01, S02, X03. Then run all cases and holdouts. These are priorities for validation, not a curated-only product menu.

## Tracking implementation requirements surfaced by this set

The current deterministic aircraft/orbital lights are insufficient. Reusable capabilities needed: entity search/disambiguation; dated flight occurrence resolution; live/historical observation adapters; satellite catalogue/orbital-element adapter and trusted propagation; a track state store; shared WorldCommands for follow, framing, replay and stop; explicit stale/predicted/playback status. Model selects and explains; adapters fetch/calculate; renderer follows. Generated images can explain an aircraft or an orbit, but cannot supply the tracking positions.

Primary implementation references checked when writing this spec:

- [OpenSky REST documentation](https://github.com/openskynetwork/opensky-api/blob/master/docs/free/rest.rst): aircraft state vectors include identifiers and position/contact timestamps. Flight-number-to-occurrence/destination resolution may require a separate flight metadata source; do not assume position feeds provide it.
- [CelesTrak GP formats](https://celestrak.org/NORAD/documentation/gp-data-formats.php): catalogue/name queries and OMM-compatible JSON support, with SGP4 mean elements. Prefer modern catalogue-capable formats rather than assuming five-digit TLE IDs. Calculated positions need the source elements and epoch recorded.

These references establish data semantics, not proof that a credentialed feed is integrated or available to this application. Provider choice, coverage, access and reuse permissions must be checked when implementing an adapter.
